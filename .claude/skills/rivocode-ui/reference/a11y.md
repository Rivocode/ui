# Accessibility: what the library already solves, and what is left to you

Each rule below is a defect that has already happened in this project and was
caught in a WCAG 2.2 AA audit of the screens. They are not hypotheses.

## What comes ready

Base UI takes care of ARIA roles, `aria-expanded`, `aria-selected`, focus
trapped in a dialog, and the wiring between label, help and error inside a
`Field`. Do not reimplement any of it, and do not add a `role` on top of a
library component: what is already there is almost always right, and yours
becomes a conflict.

What the library **cannot** know is what your content means. That is where the
rest of this page lives.

## Accessible name, and why `placeholder` does not work

Every interactive control needs a name. An icon-only button, a search field, a
row action in a table: all of them.

```tsx
<IconButton label="Exportar"><Download /></IconButton>
```

**`placeholder` is not a label.** It disappears the instant the person types,
and several screen readers do not announce it. A field with
`placeholder="Cidade"` and nothing else is a field without a name.

Prefer, in this order:

1. `Field` with `FieldLabel`: a visible label, which works for everyone.
2. `aria-label`: when the visible label is the icon itself beside it, as in a
   search.

`placeholder` is for the format example: `dd/mm/aaaa`, `minha-empresa`.

## 24px target

A clickable control is at least 24x24 CSS px. Twenty-three fails just like ten.

When the icon is smaller than that, grow the target and give the space back
with a negative margin, so the row does not get fatter:

```tsx
<button className="-my-1 flex size-6 items-center justify-center rounded-sm">
  <Info size={13} />
</button>
```

A link inside a sentence is exempt by the standard. A button is not.

## Heading order

No skipping levels: one `h1` per page, then `h2`, `h3` in order. Whoever
navigates by headings uses them as a table of contents, and a jump from `h1` to
`h3` hides the structure.

**Semantic level and visual size are different things.** An `h2` can be small:
use the size class the design asks for and keep the right tag.

## Focus and keyboard

- Never `outline-none` without restoring `focus-visible:ring-2 focus-visible:ring-ring`.
- Everything that can be clicked can also be reached with `Tab`. If you put
  `onClick` on a `div`, either it is a `button`, or it is wrong.
- `Tab` order follows DOM order. Do not fix it with a positive `tabIndex`: fix
  the DOM order.

## Never color alone

Status, error and success carry a word or an icon along, never just the tone.
People who cannot tell red from green are a large slice of any user base, and
black-and-white printing has the same problem.

A status `Badge` says "Vencida", and is not just red.

## Pitfalls by component

| Component | What to do |
|---|---|
| `OTPField` | Wrap it in a `Field` with `FieldLabel`. The first input is the one that receives the whole pasted code, and it is from it that Base UI takes the group's label: without the `Field`, that digit has no name |
| `DataTable` with `onRowClick` | The row already ignores a click that started on a button, link or field inside it. Do not add `stopPropagation` to the actions cell |
| `Checkbox`, `Radio`, `Switch` | Pass the label as a child. They wrap themselves in a `<label>`, and a `<span>` beside them wires nothing at all |
| Icon-only button | `IconButton`, with a required `label` |
| `Sidebar` on a phone | It already starts closed and closes when an item is chosen. Do not wire that by hand |
| Decorative image | `alt=""`, and not a missing `alt`. Missing makes the reader read the file name |
